# Codebase Concerns

**Analysis Date:** 2026-08-08

> Focus: technical debt, known issues, security, performance, and fragile areas in the
> `nofx` Go crypto/futures trading system (module `nofx`, ~281 Go source files, ~62k LOC).

---

## Tech Debt

### Monolithic Strategy Engine

- Issue: `kernel/engine.go` (1,516 lines) and `kernel/engine_prompt.go` (1,339 lines) concentrate candidate
  selection, market data fetch, prompt construction, decision scoring, and CLI/external data all in one place. It also
  holds ad-hoc global state caches (`vergexRankingCache`, `OITopDataMap`, `VergexDataMap`) on the engine struct
  (`kernel/engine.go:105-109,192`) with no synchronization primitive protecting writes from concurrent runs.
- Files: `kernel/engine.go`, `kernel/engine_prompt.go`, `kernel/formatter.go`
- Impact: Hard to test in isolation; changes to one subsystem (e.g. prompt building) risk silently affecting decision
  scoring. Type switches over `map[string]interface{}` (`kernel/engine.go:1013`) indicate untyped data flowing through.
- Fix approach: Split into `kernel/selection`, `kernel/prompt`, `kernel/decision` packages; type the external-data maps
  and guard shared caches with a `sync.RWMutex` or move them to a per-run context.

### Store layer dominated by GORM raw SQL and table-existence probes

- Issue: Every entity store (`store/strategy.go` 1,534 lines, `store/position.go`, `store/grid.go`, `store/decision.go`)
  interleaves GORM models with `db.Raw("SELECT COUNT(*) FROM information_schema.tables WHERE table_name = '...'")`
  migration probes (`store/ai_model.go:45`, `store/decision.go:117`, `store/equity.go:41`, `store/exchange.go:57`). This
  is a hand-rolled schema-migration pattern.
- Impact: Fragile across DB backends (the info-schema query only works on Postgres; SQLite path is special-cased). A missing
  table-probe in a new entity silently causes runtime SQL errors.
- Fix approach: Adopt a real migration tool (gormigrate, golang-migrate) so table existence is guaranteed at boot instead
  of checked on every store construction.

### Per-writer full-file SQL generated by hand

- Issue: `store` layer writes many per-column `updates[...]=...` then issues the query, e.g.
  `store/exchange.go:313-316`, `store/ai_model.go:221-243`. Branch-heavy save logic mixed with encryption fields
  (`crypto.EncryptedString`) makes field-set bugs likely.
- Files: `store/exchange.go`, `store/ai_model.go`, `store/strategy.go`
- Impact: High risk of "update without setting X" regressions; no compile-time checking of which fields were set.
- Fix approach: Prefer full-model updates or GORM `Select` with explicit field lists.

### Debug logging left in production paths

- Issue: Emoji-prefixed DEBUG logs remain in the normal create-trader and account-summary flows:
  `api/handler_trader.go:496,520,532,535` (`🔧 DEBUG:` across `CreateTrader`) and
  `trader/hyperliquid/trader_account.go:93` (`🔍 [DEBUG] Hyperliquid API ... complete data`).
- Impact: Noisy prod logs, potential PII/account-data volume, and a smell that flow was recently debugged.
- Fix approach: Remove or gate behind an explicit verbose flag.

### Two logging stacks + one `fmt.Printf`

- Issue: Repo mixes `logrus` (used in 2 files) and `zerolog` (1 file) plus raw `fmt.Printf` for operational output in
  `store/trader.go:109,135,137` and `api/strategy.go:620,628`. There is a local `logger/` package and an MCP logger
  (`logger.MCPLogger{}`).
- Files: `logger/`, `store/trader.go`, `api/strategy.go`, `kernel/engine.go`
- Impact: Inconsistent log correlation, no structured fields where `fmt.Printf` is used.
- Fix approach: Pick one structured logger (zerolog) and route all output through it; retire `fmt.Printf` in prod paths.

### Test helper uses global monkey-patching

- Issue: `github.com/agiledragon/gomonkey/v2` is a production-toolchain dependency (in `go.mod` requires), and
  `trader/testutil/test_suite.go` (665 lines) plus `market/data.go` hook into `hook.HookExec[hook.SetHttpClientResult]`
  to swap the HTTP client at runtime (`market/api_client.go:27-30`). The `hook` package is called from production code paths.
- Files: `hook/`, `market/api_client.go`, `trader/testutil/test_suite.go`
- Impact: Test doubles leaking into prod code makes runtime behavior depend on global state; gomonkey tests are brittle
  against compiler inlining changes.
- Fix approach: Consider interface-based HTTP client injection in `market/api_client.go` instead of the `hook` global.

### Large single-file trade client implementations

- Issue: Exchange adapter implementations are heavy single files: `trader/hyperliquid/trader_orders.go` (1,113),
  `provider/vergex/client.go` (979), `trader/okx/trader_orders.go` (960), each duplicating order/position/account logic.
  Order type handling is copy-pasted across adapters.
- Files: `trader/hyperliquid/trader_orders.go`, `trader/okx/trader_orders.go`, `trader/kucoin/trader_orders.go`,
  `trader/bitget/trader_orders.go`, `trader/gate/trader_orders.go`
- Impact: A bug fixed in one exchange (e.g. stop-loss vs take-profit cancellation, see
  `trader/types/interface.go:77-80`) must be manually replicated in every adapter.
- Fix approach: Extract a shared order-state machine / common order struct and reduce per-adapter surface.

## Known Bugs

### TODO tracked in production code

- Issue: Unresolved TODOs on live paths:
  - `trader/lighter/account.go:370` — "Get symbol precision from API" (precision is likely hardcoded / guessed).
  - `trader/lighter/orders.go:190` — "Check order type, only cancel stop orders" (cancel path may cancel non-stop orders).
  - `api/crypto_handler.go:78` — chain validation TODO (chain inputs not validated).
- Files: `trader/lighter/account.go`, `trader/lighter/orders.go`, `api/crypto_handler.go`
- Impact: Symbol precision and order-cancel semantics directly affect real order placement/cancellation correctness.
- Workaround: Manually auditing Lighter symbol precisions before relying on live orders.

### `market/api_client.go` allows a replaced HTTP client that drops the timeout

- Issue: `NewAPIClient` builds a client with `Timeout: 30s` (`market/api_client.go:23-24`), but the `hook` result is then
  used wholesale (`market/api_client.go:27-30`). A hook-provided client is used verbatim; if a hook returns the
  default `http.DefaultClient` (no timeout), all Binance kline/exchange calls lose request timeouts.
- Impact: Potential unbounded hangs feeding the daily/realtime data refresh loops.
- Fix approach: Enforce a timeout at call site or ensure hook clients always carry a non-zero timeout.

### Timestamp replay window allows 1-minute future skew

- Issue: `crypto/crypto.go:293` accepts timestamps up to `-1*time.Minute` in the future (`elapsed < -1 minute`), which is
  a loose bound; combined with accepting a 5-minute stale `TS`, payloads can be reused across up to ~6 minutes rather
  than the intended freshness window.
- Files: `crypto/crypto.go:284-353`
- Impact: Weaker replay protection than intended for the x402/payment encrypted payload path.
- Fix approach: Tighten future tolerance to near-zero and reduce stale window if the client clock can tolerate it.

## Security Considerations

### `.env` on disk holds production crypto keys

- Risk: A live `.env` file sits at repo root containing real `DATA_ENCRYPTION_KEY`, `RSA_PRIVATE_KEY`, `JWT_SECRET`,
  `CLAW`, and DB credentials. It is correctly gitignored (`.gitignore:34`), but it is present on the working checkout and
  any contributor/backup/screenshot workflow that includes it would leak the master encryption key and JWT secret.
- Files: `.env` (present on disk; gitignored), `.env.example` (safe template)
- Current mitigation: `.gitignore` blocks it from git; `config/config.go:96-97` refuses to boot on the insecure default
  JWT secret.
- Recommendations: Rotate whatever key values are currently in `.env` for any non-local environment; ensure CI/CD secrets
  come only from the secret store, never from a workspace `.env`; avoid `cp .env` into docker images
  (`.dockerignore` should be verified to exclude it).

### Master shared data key for all user secrets (no per-user KMS)

- Risk: One global AES `DATA_ENCRYPTION_KEY` decrypts every stored exchange API key/secret/passphrase and AI model key
  (all fields are `crypto.EncryptedString` in `store/exchange.go:28-40` and `store/ai_model.go:27`). Losing the key loses
  everything; a single compromise exposes all users' exchange credentials.
- Files: `crypto/crypto.go:56-106`, `store/exchange.go`, `store/ai_model.go`
- Current mitigation: Field-level encryption with AAD; `EncryptedString.Value()` fails closed on encrypt errors
  (`crypto/crypto.go:459-467`) so it will not persist plaintext secrets.
- Recommendations: Move toward per-record/per-user data keys wrapped by the master RSA key, and document key-rotation
  procedure (currently there is none in-code).

### x402 signing wallet key lives in a single env var

- Risk: A single `CLAW402_WALLET_KEY` (hex ECDSA private key for the auto-payment wallet) is loaded directly from the
  environment in `kernel/engine.go:211`, `provider/nofxos/claw402.go:36`, `provider/nofxos/client_resolve.go:17`, and
  `provider/vergex/client.go:81`. It is not present in `.env.example` (undocumented), so operators may not realize it is
  required, and its exposure permits automated off-chain payment settlement on the user's behalf.
- Files: `provider/nofxos/client_resolve.go`, `provider/nofxos/claw402.go`, `provider/vergex/client.go`, `kernel/engine.go`
- Current mitigation: Loaded only from env, never logged.
- Recommendations: Add to `.env.example` documentation, consider hardware-wallet or KMS custody, and add explicit spend
  limits.

### SSRF guard can be fully disabled

- Risk: `allowLocalCustomAPI()` (`security/url_validator.go:24-27`) returns false (permissive) whenever
  `ALLOW_LOCAL_CUSTOM_API` is non-empty and non-"0"/"false". Setting `ALLOW_LOCAL_CUSTOM_API=1` disables loopback/private
  blocking *globally*, not just for the custom provider path, despite the function comment describing it as a narrow,
  opt-in escape hatch.
- Files: `security/url_validator.go:24-98`, `security/url_validator.go:175-223` (`SafeHTTPClient`)
- Current mitigation: Default is OFF (absent env var); blocked host list and DNS-rebinding-aware `LookupIPAddr` check are
  thorough when enabled (`security/url_validator.go:144-170`).
- Recommendations: Scope the opt-in flag to the custom-provider URL path only, and never disable the DNS-rebinding IP
  re-check. Verify `ALLOW_LOCAL_CUSTOM_API` is not set in prod deployments.

### CORS wildcard warning only advisory

- Risk: `api/server.go:92-108` warns when `CORS_ALLOWED_ORIGINS` is `*` but proceeds, reflecting any origin with
  credentials depending on deployed config. Single-user production deployments (Railway) may run with wildcard CORS.
- Files: `api/server.go:65-110`
- Current mitigation: Warn log only; defaults to localhost origins when unset.
- Recommendations: Refuse to start (or force explicit opt-in) when `CORS_ALLOWED_ORIGINS=*` in production mode.

### JWT secret required but rotation/documentation unclear

- Risk: `config/config.go:96-97` hard-fails on the insecure default, which is good. But `auth/auth.go` keeps a purely
  in-memory `tokenBlacklist` (up to 100,000 entries) per process (`auth/auth.go:16-63`) — restarting the process drops the
  blacklist, so a logged-out token becomes valid again until its 24h expiry (`auth/auth.go:90`).
- Files: `auth/auth.go`, `config/config.go`
- Current mitigation: Blacklist sweep protects memory; boot fails on default secret.
- Recommendations: Move logout invalidation to a shared/persistent store (Redis/DB) if multi-instance deployment is
  planned; otherwise document that logout is process-local.

### Overly broad static-check exemptions

- Risk: `staticcheck`/`go vet` / security scanner rules appear disabled broadly (no per-file rationale evident). No
  obvious `//nolint` scoping is visible in the reviewed hot paths.
- Files: whole repo
- Recommendations: Run `gosec` and `govulncheck`, and scope any lint suppressions to specific lines with justification.

## Performance Bottlenecks

### Map-backed per-symbol data mutated across goroutines

- Problem: `StrategyEngine` holds `MarketDataMap`, `MultiTFMarket`, `OITopDataMap`, `QuantDataMap`, `VergexDataMap`
  (`kernel/engine.go:105-109`) and writes `e.vergexRankingCache = make(...)` (`kernel/engine.go:770`) with no lock, while
  fetch loops spawn goroutines behind `sync.WaitGroup` (`kernel/engine.go:1166,1200,1253-1259`).
- Files: `kernel/engine.go`
- Cause: Field writes occur concurrently during batched fetch while other goroutines/middleware read the maps.
- Improvement path: Add `sync.RWMutex` guarding shared caches or snapshot the maps per run; run under `-race` to confirm.

### Repeated raw table-existence SQL per entity construction

- Problem: Every `store` init executes `SELECT COUNT(*) FROM information_schema.tables ...` on Postgres (`store/ai_model.go:45`,
  `store/decision.go:117`, `store/equity.go:41`, `store/exchange.go:57`). Constructing many stores at boot multiplies
  `information_schema` queries.
- Files: `store/driver.go`, `store/*.go`
- Cause: Hand-rolled per-store schema probe.
- Improvement path: Run migrations once at boot; drop per-store probes.

### `context.Background()` everywhere in exchange clients

- Problem: All Binance calls use `Do(context.Background())` — `trader/binance/futures_orders.go:52-732`
  (dozens of sites), `trader/binance/futures_account.go:26-281`, `trader/binance/futures_positions.go:27-220`. A hung
  exchange endpoint blocks the goroutine indefinitely since the HTTP client is per-call and not necessarily time-bounded.
- Files: `trader/binance/*`
- Cause: No deadline/cancellation propagation from the loop/trader context into exchange SDK calls.
- Improvement path: Thread the trader/order context through and enforce per-call timeouts.

### Website production bundle committed

- Problem: `web/` tree (197 tracked files) includes `web/dist` build output in git.
- Files: `web/dist`
- Impact: Merge conflicts on every rebuild; larger repo; stale artifacts may be served if deployments use the built files
  directly.
- Improvement path: Gitignore `web/dist` and build in CI/CD.

## Fragile Areas

### Order cancellation semantics vary per exchange adapter

- Files: `trader/types/interface.go:77-80` (explicitly documents "BUG fix: don't delete take-profit when adjusting
  stop-loss" and vice-versa), `trader/hyperliquid/trader_orders.go`, `trader/okx/trader_orders.go`,
  `trader/kucoin/trader_orders.go`, `trader/lighter/orders.go:190`
- Why fragile: Correctness of stop-loss/take-profit adjustment depends on each adapter canceling the *right* order type;
  a mismatch causes unintended order cancellation in live trading.
- Safe modification: Add adapter-level "cancel only stop / only take-profit" unit tests using the test suite in
  `trader/testutil/test_suite.go`; validate against each exchange's API docs.
- Test coverage: `trader/kucoin/order_sync_test.go` (628 lines) exists but no parity across other adapters.

### Order execution + auto-grid loop concurrency

- Files: `trader/auto_trader.go` (mutex-guarded `isRunning`, `peakPnLCacheMutex`, `runtimeHealthMu`), `trader/auto_trader_grid.go`,
  `trader/auto_trader_grid_levels.go`, `trader/auto_trader_loop.go` (reads/writes `at.peakPnLCacheMutex`, `at.isRunningMutex`)
- Why fragile: Grid level (re)balancing and order sync run in goroutines; any lock-ordering mistake can deadlock or double-order.
- Safe modification: Keep all concurrency confined to the mutex-protected methods; add `-race` tests; avoid adding new
  goroutines that touch shared `peakPnL`/`isRunning` without taking the named locks.

### Lighter trading module (new integration)

- Files: `trader/lighter/trading.go` (974 lines), `trader/lighter/trader.go` (691 lines), `trader/lighter/account.go`,
  `trader/lighter/orders.go`
- Why fragile: Several unresolved TODOs (precision, order-type cancel), and `integration_test.go` (1,108 lines) is the
  largest test file — sign of a fast-moving, not-yet-stable integration.
- Safe modification: Treat any Lighter change as high-risk; keep the integration test green before/after.

### Single-process / single-user architecture assumptions

- Files: `auth/auth.go` in-memory blacklist, `api/server.go` single-instance routes, `.env`-based config
- Why fragile: Any multi-replica or multi-user deployment breaks logout revocation, per-user isolation, and key custody.
  The UI and CLI log in with `system`/single account patterns.

## Scaling Limits

**Process memory:**
- Current: In-memory token blacklist capped at 100,000 entries (`auth/auth.go:23`) — hard ceiling on signed-out tokens
  before drift.
- Limit: Beyond 100k entries, memory grows unbounded until a sweep; entries only removed on access.
- Scaling path: Persistent logout store (Redis/DB) or shorter JWT TTL.

**Exchanges/adapters:**
- Current: 8+ exchange adapters with duplicated order logic.
- Limit: Each new exchange multiplies the fragile cancel/precision surface.
- Scaling path: Shared order middleware + adapter-wide integration tests.

**Market data fan-in:**
- Current: every engine run fetches `MarketDataMap` for all candidate symbols plus vergex batch ranking.
- Limit: Symbol lists and per-symbol multi-timeframe data (`MultiTFMarket`) scale linearly; bound by provider rate limits.
- Scaling path: Batch endpoints already partly in place (`FetchVergexDataBatch` `kernel/engine.go:1122`); add shared rate
  limiting and caching.

## Dependencies at Risk

**Bybit / Lighter / Aster adapters use fast-moving SDKs:**
- Risk: `github.com/bybit-exchange/bybit.go.api` (`v0.0.0-2025...` pseudo-version) and
  `github.com/elliottech/lighter-go` (`v0.0.0-...`), `github.com/sonirico/go-hyperliquid` — pseudo-versions with
  unstable APIs; upstream breaking changes break adapters silently.
- Files: `go.mod`, `trader/bybit/trader_orders.go`, `trader/aster/trader_orders.go`, `trader/hyperliquid/*`
- Impact: Unexpected build/behavior regressions on `go get -u`.
- Migration plan: Pin exact pseudo-versions (already) and add CI that runs `go build` + integration tests on dependency
  bumps; prioritize adapters where unsigned fees/orders matter.

**Heavy indirect crypto/ZK toolchain:**
- Risk: `zkvm_runtime`, `gnark-crypto`, `supranational/blst`, `ethereum/c-kzg-4844` bloat the binary for payment/lighter
  features. `go-ethereum v1.17.3` and `modernc.org/sqlite` add significant size.
- Files: `go.mod` (indirect requirements)
- Impact: Large binary/attack surface; `nofx` binary already ~62MB on disk.
- Migration plan: Vendor if needed; audit indirect deps for known CVEs.

## Missing Critical Features

**Key rotation workflow:**
- Problem: No key-rotation procedure for `DATA_ENCRYPTION_KEY` / `RSA_PRIVATE_KEY`; rotating breaks all stored secrets.
- Blocks: Safe credential refresh in production.

**Multi-instance / multi-user isolation hardening:**
- Problem: In-memory blacklist, single global crypto service (`crypto.SetGlobalCryptoService`, `crypto/crypto.go:409`),
  and single-user auth assume one process, one identity.
- Blocks: Horizontal scaling and true multi-tenancy.

**Policy/guardrail for AI decision to order placement:**
- Problem: Execution path from LLM decision to order relies on many hardcoded risk defaults in prompt building
  (`kernel/engine_prompt.go:499-584`). There is no config-driven, audited stop on "aggressive mode" positioning across adapters.
- Blocks: Consistent risk governance across all supported exchanges.
